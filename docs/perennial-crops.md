# Perennial crops

`game-data/crops.ts` defines annual/perennial kind, unlock, planting cost, cap, durations, output and visual stages. `PerennialCropKey` and its command schema derive from those definitions. Existing annual barley commands and batch workflows deliberately reject perennial crops.

`game-core/farm/perennialCrops.ts` contains pure eligibility and route planning. `tend_perennial_crop` is sent before travel; the server locks the farm, validates availability, land, money and storage, debits the sapling purchase atomically, reserves the tile with a crop row, and saves `production.cropWork`. Expected farm versions prevent duplicate starts/payments. Payment receipts use the `crop_planting` ledger type (migration 0051).

The job stores outbound and inbound paths and travel/work/delivery deadlines. `perennialCropLifecycle.ts` settles it under the farm lock during normal reconciliation. The persisted settled receipt makes repeats harmless. Maturity derives from the original `plantedAt`, while `growthCompletesAt` advances after harvests. New harvests always collect the full configured yield (2 baskets), checking capacity before any crop mutation. `cropYields` remains for compatibility with already accepted legacy partial jobs; new jobs normalize it to the full yield. The farmer stays reserved throughout delivery, preventing simultaneous palm harvests. Only this workflow adds date baskets, so its saved quantity reserves room exclusively; before adding trading or porter harvesting, all new writers must also subtract active crop-work reservations.

`dates` remains the persisted inventory key, now measured in baskets. It is excluded from shared farm/warehouse storage limits: `WAREHOUSE_DATE_BASKET_CAPACITY` grants five slots only when a warehouse is complete. Allocation and route planning never fall back to the farm or granary. Legacy stock above five is preserved (shown in warehouse stock and unable to accept new harvests), and already accepted jobs retain their saved timeline; no destructive inventory migration is performed. Both the frontend and the server require room for both baskets, not just one. Barley multi-field workflows exclude palms.

React requests work and refreshes at its deadline. Phaser interpolates the same saved timeline; it never sends harvest-completion commands. Tab closure, scene changes and throttled animation cannot postpone accepted work. A visible tab's next snapshot restores the endpoint even if it missed the journey. The dates-treat timestamp lives in the existing production JSON so older saves remain valid without default-data rewrites.

To add another perennial: add its crop/inventory definitions and sprite assets, storage capacity and placement/unlock rules, then expose a crop action and popup. The generic saved work service and lifecycle handle its timers and output. Add a treat or market entry only if explicitly supported, and extend reservations before adding another inventory producer. Keep player-facing balance in `game-rules.md` aligned.

Initial tuning: 25 shekels, 2 palms, 2 baskets per harvest, first fruit at 24 hours, then 12-hour ripening, five baskets in the warehouse only; one basket as a treat gives +10 with an independent 8-hour cooldown. Dates are not market goods yet.
